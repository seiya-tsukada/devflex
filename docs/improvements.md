# 改善ポイント

Vercel へのデプロイに向けたリファクタリングの時点で把握している課題と、対応の方向性をまとめます。上から優先度の高い順です。

## 1. Vercel 上のデータがメモリにしか残らない

**現状**

保存先は [server/store.ts](../server/store.ts) の `KeyValueStore` で切り替わります。

| 実行環境 | 保存先 |
| --- | --- |
| ローカル（`npm run dev` / `npm start`） | `.data/kv-store.json`（JSON ファイル） |
| Vercel（環境変数 `VERCEL` あり） | 関数インスタンスのメモリ |

Vercel のファイルシステムは読み取り専用かつインスタンスごとに独立しているため、ファイルには保存できません。外部ストアは現時点では使わない方針なので、メモリに保存しています。

**起きること**

- 関数インスタンスが破棄されると、作成したプロジェクト・タスク・実行履歴などがすべて消えます。デモワークスペースはサンプルデータに戻ります。
- セッションもメモリにあるため、インスタンスが変わるとログイン状態が消え、`401` で再ログインを求められます。
- アクセスが増えてインスタンスが複数になると、ログインしたインスタンスと別のインスタンスにリクエストが届き、ログイン直後でも `401` になることがあります。データもインスタンスごとにバラバラになります。
- デプロイのたびにデータがリセットされます。

デモとして見せる用途なら許容できますが、データを残したい段階になったら外部ストアが必要です。

**対応方針**

- `KeyValueStore`（`get` / `set` / `del`、TTL 付き）を実装したクラスを 1 つ追加し、`createStore()` で選ぶだけで切り替えられます。API 側の変更は不要です。
- 候補：マネージド DB（Postgres など）、Vercel Blob、KV ストア。
- 本格的に使うなら、下記 2 の理由から、キーバリューではなくテーブル設計の DB への移行を検討します。

## 2. 同じユーザーの同時更新で後勝ちになる

**現状**

ユーザーごとのデータ（プロジェクト、タスク、エージェント、実行、ログ、設定、シークレット）を 1 つのドキュメント（`Workspace`）として読み書きしています。各リクエストはワークスペース全体を読み込み、変更があれば全体を書き戻します（[server/routes/api.ts](../server/routes/api.ts) の `requireAuth`）。

**起きること**

- 同じユーザーのリクエストが並行すると、後から保存した方で上書きされ、先の変更が消えることがあります。
- 画面は実行中に 1.2〜1.5 秒間隔でポーリングしており、ポーリングでもモック実行の進行（下記 4）で書き込みが発生するため、編集操作と競合する可能性があります。
- 外部ストアを入れても、この構造のままでは同じ問題が残ります。

**対応方針**

- エンティティ単位（プロジェクト・タスク・実行ごと）に保存する。
- またはバージョン番号による楽観的ロックを入れ、競合時は再試行する。
- DB に移行する場合はトランザクションで更新する。

## 3. 認証が実質的にない

**現状**

メールアドレスを入力するだけでサインインでき、未登録なら自動でユーザーが作られます。パスワードや本人確認はありません。

**起きること**

- 他人のメールアドレスを入力すれば、その人のワークスペースに入れます（なりすまし）。
- 誰でも無制限にユーザーを作れます。

公開 URL にデプロイする前提では最も重要なセキュリティ課題です。

**対応方針**

- OAuth（GitHub など）やマジックリンクによる本人確認を導入する。
- それまでの暫定策として、Vercel の Deployment Protection（パスワード保護など）で公開範囲を絞る。
- ログイン API にレート制限を入れる。

## 4. 共有のデモワークスペース

**現状**

「デモワークスペースで試す」は全訪問者が同じ `demo-user` のワークスペースを共有します。

**起きること**

- 誰かがデモデータを削除・変更すると、他の訪問者にも反映されます。
- 上記 2 の後勝ちが、異なる訪問者の間でも起きます。

**対応方針**

- 訪問者ごとにデモワークスペースを複製する。
- または定期的にリセットする、デモは読み取り専用にする。

## 5. シークレットが平文で保存される

**現状**

API キーや GitHub トークンは、クライアントにはマスクした値しか返しません。ただし保存先には平文で入っています。

**対応方針**

- 環境変数で渡した鍵で暗号化してから保存する。外部ストアを導入するタイミングで合わせて対応するのがよいです。
- 実プロバイダー連携を始める前に対応が必要です。

## 6. モック実行は「読まれたとき」に進む

**現状**

サーバーレスではレスポンスを返した後のタイマー（`setTimeout`）が動かないため、モック実行は経過時間から状態を計算し、リクエストのたびに追いつかせています（`advanceSimulatedExecutions`、[server/services/agentAdapters.ts](../server/services/agentAdapters.ts)）。

**起きること**

- 誰も画面を開いていない間は状態が進みません。次にアクセスしたときにまとめて進み、ログの時刻は本来の予定時刻で記録されます。
- 表示上の問題はありませんが、「完了時に通知する」のようなサーバー側の処理はこの方式では作れません。

**対応方針**

- 実プロバイダーの実行は数分〜数十分かかり、関数の実行時間上限（現在 `maxDuration: 30` 秒）を超えます。リクエストの中で実行を待つのではなく、外部ワーカー・キュー・Webhook でのコールバックで状態を更新する設計が必要です。

## 7. ポーリングの負荷

**現状**

実行中は 1.2〜1.5 秒、それ以外も 3〜4 秒間隔で API を呼びます。各リクエストでワークスペース全体を読み込み、変更の有無を判定するために JSON に変換しています。

**起きること**

- Vercel 上では関数の呼び出し回数と実行時間がそのまま利用量になります。
- データが増えるほど 1 回のリクエストが重くなります。

**対応方針**

- ポーリング間隔を延ばす、タブが非表示のときは止める。
- 必要なデータだけを読む構造にする（上記 2 と同じ対応）。
- Server-Sent Events などのプッシュ型への置き換えを検討する。

## 8. データ量の上限がない

**現状**

アクティビティログは 1,000 件で切り詰めていますが、実行履歴とその段階別ログには上限がありません。すべてが 1 つのワークスペースに入るため、使うほど読み書きが重くなります。

**対応方針**

- 実行履歴の保持期間を決めて古いものを削除する、またはアーカイブする。
- 一覧 API にページネーションを入れる。

## 9. Vercel ビルドが独自スクリプト

**現状**

[scripts/build-vercel.ts](../scripts/build-vercel.ts) が Vite の SSR ビルドで API を 1 ファイル（約 1MB）にまとめ、Build Output API の形式（`.vercel/output`）で出力しています。ローカルでは出力された関数を直接動かして動作を確認済みです。

**注意点**

- 実際の Vercel 環境へのデプロイはまだ確認していません。
- ランタイム（`nodejs22.x`）、`maxDuration` などの関数設定はスクリプト内に直接書いています。
- `vercel dev` はこの出力を使いません。ローカル開発は `npm run dev` を使います。
